# AXIOM — Globe 3D « crises géopolitiques & chokepoints » : rendu + sources live (faisabilité)

> **Doc de recherche · 2026-07-10.** Cible : un globe affichant en live les crises/tensions géopolitiques et les zones critiques d'approvisionnement (détroits/chokepoints), terminal perso mono-utilisateur, budget **0 $/mois visé, plafond dur 30 $/mois**, **aucune nouvelle dépendance npm sans nécessité réelle documentée**.
> Méthode : **vérification empirique en direct** (`curl` réel + fetch réel des endpoints, pas de lecture de page marketing seule) le 2026-07-10, complétée de lecture de doc officielle pour le cadrage légal/tarifaire. Mesures de poids de bundle prises sur le build réel d'AXIOM (`apps/web/dist`) et sur Bundlephobia/unpkg pour les libs candidates.
> **Ce doc complète, sans les redire, deux recherches déjà faites le même jour** : `06-trafic-aerien-globe.md` (OpenSky/ADS-B pour le trafic aérien) et `07-trafic-maritime-petroliers-live.md` (IMF PortWatch déjà creusé en détail pour le trafic maritime/pétrolier par chokepoint). Ici : (1) le choix de la techno de **rendu** du globe — angle non couvert par 06/07 — et (2) la couche **crises/conflits géopolitiques**, qui est un besoin distinct du trafic aérien/maritime.
> **Verdict en une phrase :** le rendu doit être **D3 (`d3-geo`) + Canvas 2D**, pas WebGL/three.js — le gain visuel du 3D ne justifie pas +200 à +500 Ko gzip sur un bundle qui pèse aujourd'hui 272 Ko gzip en tout ; côté données, les **chokepoints sont bien couverts** (PortWatch + Kiel, cf. §5), mais une **« situation live des conflits »** fiable et gratuite **n'existe pas** — le meilleur compromis honnête combine un flux d'événements bruts (GDELT), un flux confirmé mais lent (UCDP) et une couche spécifique Ukraine (ISW), aucun n'étant un vrai équivalent gratuit d'ACLED.

## 1. Rendu du globe — comparatif empirique (question qui conditionne tout le reste)

**Mesure de référence prise dans le repo AXIOM lui-même** (`apps/web/dist`, build de prod actuel, 20 fenêtres + tous les indicateurs) :

```
index-*.js : 944 437 o bruts → 272 549 o gzip (mesuré par gzip -c, pas une estimation)
```

C'est le bundle JS **entier** de l'app aujourd'hui. Toute lib candidate doit être jugée contre ce chiffre, pas dans l'absolu.

| Option | Poids gzip mesuré | Dépendances transitives | Paradigme de rendu | Catch |
|---|---|---|---|---|
| **`react-globe.gl`** (= `globe.gl` + `three` + `three-globe` + `d3-*` + `h3-js` + `polished` + …) | **508,7 Ko gzip** (1,81 Mo brut), mesuré via l'API Bundlephobia sur `react-globe.gl@2.38.0` — **~40 paquets transitifs** dont `three` (2,9 Mo brut à lui seul) et `h3-js` (379 Ko brut, système d'indexation géo hexagonale — inutile ici) | `globe.gl`, `three-globe`, `react-kapsule`, `d3-scale`, `d3-geo`, `tinycolor2`, `polished`, `h3-js`, `earcut`, `delaunator`… (liste exhaustive obtenue en direct) | Scene graph Three.js managé par un wrapper impératif (`react-kapsule`) — API très haut niveau (marqueurs, arcs, heatmap "prêts à l'emploi") | **Ajouter cette lib ferait +187 % sur le bundle JS gzippé actuel de tout AXIOM**, pour une seule fenêtre parmi 20. Aucune "nécessité réelle documentée" ne justifie ce ratio dans ce budget. |
| **`three` + `@react-three/fiber`** (globe fait main : sphère + texture + markers custom, sans `globe.gl`/`three-globe`) | `three` seul : **182,4 Ko gzip** (725,9 Ko brut, 0 dépendance) + `@react-three/fiber` : **50,9 Ko gzip** (159,8 Ko brut) → **~233 Ko gzip combinés**, avant d'écrire la moindre ligne de code perso (texture terre, éclairage, caméra/orbit, raycasting hover) | `three` (peer), rendu WebGL réel | React reconciler pilotant une scène WebGL — **paradigme différent** de tout ce qui existe dans AXIOM aujourd'hui (klinecharts et le treemap `MarketMapWindow.tsx` sont du canvas 2D piloté par ref/rAF, **pas** un reconciler React) | **+86 % sur le bundle gzippé actuel**, pour refaire à la main (éclairage, UV-mapping des frontières, hover/hit-testing 3D) ce que `globe.gl` offre gratuitement — donc ni le gain de poids de la 1ʳᵉ option, ni la simplicité de la 3ᵉ. Le pire des deux mondes pour ce budget. |
| **D3 (`d3-geo` uniquement) + Canvas 2D, projection orthographique** | **13,1 Ko gzip** (36,3 Ko brut, mesuré directement sur le fichier `d3-geo.min.js@3.1.1` via `unpkg` + `gzip -c` — le chiffre Bundlephobia officiel pour ce paquet était visiblement erroné/tronqué au moment du test, écarté) | **Une seule lib, `d3-geo`** — pas de `d3-selection` nécessaire : `d3.geoPath().context(ctx)` dessine directement dans un `CanvasRenderingContext2D`, sans DOM/SVG (confirmé sur la doc officielle `d3js.org/d3-geo/path`) | **Canvas 2D + ref + boucle `requestAnimationFrame` perso, zéro re-render React par frame** — c'est **exactement** le pattern déjà en place dans AXIOM : `MarketMapWindow.tsx` (treemap canvas + `ResizeObserver` + refs, "pas de state React" par design, commentaire du fichier) et le spike `WebGLSyncSpike.tsx` (canvas overlay découplé de React) | Rotation/drag-to-spin, hover/hit-test sur les marqueurs et clipping de l'hémisphère caché sont **à coder soi-même** (pattern D3 orthographique très documenté, pas une zone grise) — plus de travail manuel que `globe.gl`, mais du même ordre que le hit-testing déjà écrit pour le treemap. Un fond de frontières (TopoJSON 110m, ~25-30 Ko gzip) est **optionnel** : un globe "marqueurs + graticule" sans tracé de pays est même plus lisible pour ce cas d'usage précis (tension géopolitique par point, pas cartographie politique détaillée) et ne coûte aucune donnée supplémentaire. |

**Reco AXIOM — tranchée : D3 (`d3-geo`) + Canvas 2D.** C'est la seule des 3 options qui respecte la contrainte "aucune dépendance sans nécessité réelle" au sens strict : une seule lib, ~13 Ko gzip (5 % du bundle actuel, pas 87-187 %), et qui **prolonge un pattern déjà en place** dans le code (canvas+ref+rAF, zéro re-render React sur donnée haute fréquence) plutôt que d'en introduire un nouveau (reconciler React-Three-Fiber piloté par état React, potentiellement en tension avec l'exigence "pas de re-render React sur données haute fréquence"). Le "globe 3D immense" en WebGL est visuellement plus impressionnant, mais rien dans la demande ne justifie de payer 200 à 500 Ko gzip supplémentaires pour ça dans un budget 0-30 $/mois construit fenêtre par fenêtre. `d3-geo` est la seule nouvelle dépendance que je recommanderais réellement d'ajouter ici — parce que réimplémenter soi-même le clipping de sphère/rotation orthographique correctement (cas limites aux pôles, antiméridien) coûterait probablement plus cher en temps/bugs que ces 13 Ko.

## 2. GDELT — la couche "événements géolocalisés" existe, mais pas là où la doc officielle le dit

AXIOM utilise déjà GDELT DOC 2.0 (`api.gdeltproject.org/api/v2/doc/doc`, mode `artlist`) pour la fenêtre NEWS — recherche texte, pas de géolocalisation structurée. La question posée était : existe-t-il une couche "événements géopolitiques géolocalisés" exploitable pour un globe ?

| Source | Couverture | Auth | Rate limit | Format | Fréquence | Catch |
|---|---|---|---|---|---|---|
| **GDELT DOC 2.0 API** (déjà branché, `mode=artlist`) | Recherche texte plein, pas de géo structurée par événement | Aucune | **Confirmé en direct : HTTP 429 "Please limit requests to one every 5 seconds"** dès qu'on dépasse ce rythme — comportement réel, pas juste documenté | JSON | Continu | N'apporte rien de nouveau ici — déjà utilisé, pas une source d'événements géolocalisés |
| **GDELT GEO 2.0 API** (`api.gdeltproject.org/api/v2/geo/geo`, `mode=PointData`) — **la couche que les billets de blog officiels décrivent comme LA réponse à ce besoin** | Documentée pour produire un GeoJSON de points par mention géographique | — | — | GeoJSON | "Toutes les 15 min" (doc) | **Endpoint mort, confirmé empiriquement à 3 reprises** (casse de paramètre différente à chaque fois, y compris l'URL exacte citée dans le billet officiel `blog.gdeltproject.org/gdelt-geo-2-0-api-debuts`) : réponse `HTTP 404` avec en-tête `Server: GDELT Server` — un vrai 404 applicatif, pas un blocage de rate-limit (le message de rate-limit de GDELT est un texte brut distinct, bien identifié par ailleurs dans ce même test). **La doc officielle décrit une API qui n'existe plus en pratique en 2026**, sans mention de dépréciation trouvée. |
| **GDELT 2.0 Event Database — fichiers bruts** (`data.gdeltproject.org/gdeltv2/{TIMESTAMP}.export.CSV.zip`) — **la vraie trouvaille** | Mondiale, tous événements CAMEO codés (protestations, actes militaires, déclarations diplomatiques…), avec **acteurs, code d'événement, score de ton/intensité, ET géolocalisation** | **Aucune** — confirmé en direct, fichier `lastupdate.txt` + `.export.CSV.zip` téléchargés sans clé ni compte | Aucun rate-limit rencontré sur ce host distinct (différent de `api.gdeltproject.org`) | **CSV tabulé, 61 colonnes, SANS ligne d'en-tête** (schéma à coder en dur côté client — testé : 943 événements dans la tranche 2026-07-10 21:15, 922/943 (**97,8 %**) avec `ActionGeo_Lat`/`ActionGeo_Long` non vides) | **Toutes les 15 minutes**, confirmé (`lastupdate.txt` pointe vers un fichier daté à la minute près de la requête) | Deux catches réels : (1) **ce host ne répond qu'en HTTP, pas HTTPS** (testé : `https://data.gdeltproject.org/...` → échec de connexion ; `http://` → 200 OK) — le proxy générique `/extapi/<hôte>` du daemon (`apps/daemon/src/proxy.ts`) construit aujourd'hui systématiquement une URL amont en `https://` (ligne `urlAmont = https://${hote}...`), donc **une route dédiée forçant `http://` est nécessaire**, pas juste un ajout à l'allowlist ; (2) le fichier est un **.zip réel (compression DEFLATE, ratio ~6x observé)**, pas un simple gzip — il faut soit une mini-lecture d'en-tête ZIP local (format simple, faisable en ~30-50 lignes de JS avec `DataView`) combinée à l'API native `DecompressionStream('deflate-raw')` du navigateur (zéro nouvelle dépendance npm), soit accepter cette complexité d'implémentation comme coût réel du "vrai live" par rapport aux autres sources JSON déjà branchées dans AXIOM (qui n'ont jamais eu ce problème). |

**Reco AXIOM :** la couche "événements géolocalisés" que la demande cherchait **existe bel et bien**, mais c'est le flux brut `data.gdeltproject.org/gdeltv2/*.export.CSV.zip` — pas l'API GEO 2.0 documentée par le blog officiel (morte) ni l'API DOC déjà branchée (pas géolocalisée). Techniquement viable à 0 $, zéro clé, cadence 15 min parfaitement alignée avec un polling "live" raisonnable — mais c'est le morceau le **plus lourd à construire** de tout ce rapport (schéma 61 colonnes sans en-tête à documenter en dur, dézippage DEFLATE côté client, route proxy dédiée en `http://`). Filtrer ensuite côté client sur `QuadClass` (1-2 = coopération, **3-4 = conflit verbal/matériel** — c'est le signal "tension géopolitique" recherché) et `GoldsteinScale` (intensité -10 à +10) pour ne garder que le signal pertinent, pas les ~90 000 événements/jour bruts.

## 3. ACLED — la source de référence, mais pas gratuite pour un projet perso

| Test | Résultat empirique |
|---|---|
| Registration | Confirmée gratuite et ouverte à tous (formulaire myACLED), aucune adresse institutionnelle exigée |
| **Accès API réel avec une adresse générique (gmail)** | **Bloqué structurellement.** La doc officielle (`myacled-faqs`) est explicite : un compte enregistré avec une adresse générique (gmail.com) est automatiquement placé sur le tier **"Open myACLED"**, qui donne accès au dashboard web (Explorer, Conflict Index, cartes) **mais explicitement PAS à l'API**. L'accès API est réservé aux tiers **Research/Partner/Enterprise**, qui nécessitent une affiliation organisationnelle/académique |
| **Test en direct sans token** (`acleddata.com/api/acled/read?limit=1`) | `HTTP 403 {"message":"Access denied"}` — cohérent avec un mur d'accès réel, pas juste un paramètre manquant |
| **Corroboration terrain** | Un projet open-source comparable (`koala73/worldmonitor`, GitHub issue #290) rapporte que son token ACLED a été explicitement rejeté ("ACLED rejected this token") — friction réelle même pour des porteurs de token, pas seulement une question théorique de tier |
| Clause EULA notable | Les CGU interdisent l'usage des données ACLED pour "entraîner, tester, développer ou améliorer" des modèles IA/LLM — sans impact direct ici (AXIOM afficherait, n'entraînerait pas), mais à noter puisque le produit est bâti avec un outil IA |

**Reco AXIOM : écarter comme source gratuite pour un projet perso.** C'est la source la plus citée/réputée pour les conflits armés, mais **le tier gratuit exclut explicitement l'API** — ce n'est pas une question de patience ou de bon formulaire, c'est un mur d'accès documenté. Sans affiliation académique/organisationnelle, il n'y a pas de chemin gratuit vers cette donnée dans ce projet.

## Synthèse — architecture recommandée pour le globe (4 couches empilées)

| Couche | Source(s) | Statut | Fraîcheur réelle | Rôle |
|---|---|---|---|---|
| **Rendu** | `d3-geo` (Canvas 2D, projection orthographique) | 1 nouvelle dépendance justifiée (~13 Ko gzip) | — | Socle graphique, pattern canvas+ref+rAF déjà en place dans AXIOM |
| **Chokepoints (approvisionnement)** | IMF PortWatch (primaire, déjà validé doc 07) + Kiel (secondaire, mer Rouge/Panama/Malacca/Cap) | Gratuit, robuste, 0 clé | Hebdo (PortWatch) / quotidien (Kiel) — **jamais du live seconde-par-seconde, à afficher honnêtement** | La couche la plus solide du rapport |
| **Événements géopolitiques "rapides"** | GDELT Event Database 2.0 brute (`.export.CSV.zip`), filtrée `QuadClass`≥3 | Gratuit, 0 clé, mais **coût d'implémentation réel** (schéma 61 col. sans en-tête, dézippage DEFLATE, route proxy `http://` dédiée) | 15 min | Signal rapide mais bruyant (toute tension verbale/matérielle mondiale) |
| **Conflits "confirmés" (lents)** | UCDP Candidate GED CSV | Gratuit, 0 clé, proxy nécessaire (pas de CORS) | ~1 mois de lag | Vérité terrain plus lente, vient calmer le bruit de GDELT |
| **Overlay Ukraine (bonus)** | ISW ArcGIS FeatureServer (reverse-engineered) | Gratuit, 0 clé, CORS ouvert | Rythme des analyses ISW (non contractuel) | Enrichissement scope-limité, zone grise documentaire (comme CBOE GEX) |

## Reco AXIOM — tranchée

1. **Rendu : `d3-geo` + Canvas 2D.** C'est la seule des trois options qui respecte à la fois le budget (~13 Ko gzip vs +187 % ou +86 % du bundle actuel pour les deux options WebGL) et la contrainte "aucune dépendance sans nécessité réelle" — et elle prolonge un pattern déjà éprouvé dans AXIOM (canvas+ref+rAF, zéro re-render React par frame, cf. `MarketMapWindow.tsx`/`WebGLSyncSpike.tsx`) plutôt que d'introduire le paradigme React-Three-Fiber. Le "globe 3D immense" en WebGL serait plus spectaculaire visuellement, mais rien dans la demande ne documente une nécessité qui justifierait 200-500 Ko gzip pour une seule fenêtre parmi 20.
2. **Chokepoints : ne rien refaire, brancher IMF PortWatch (doc 07) + Kiel en secondaire.** C'est la partie la plus solide de toute cette recherche — gratuite, sans clé, et pour PortWatch, sans même besoin de proxy.
3. **Crises géopolitiques : il n'y a PAS de source gratuite équivalente à ACLED, et il faut le dire clairement à l'utilisateur plutôt que de bricoler une fausse promesse de "live".** Le combo le plus honnête et gratuit trouvé est : GDELT Event Database brute (rapide, bruyant, complexe à implémenter côté dézippage/proxy) + UCDP Candidate GED (lent mais confirmé, létalité incluse) + ISW en overlay Ukraine (zone grise documentaire, scope limité). Aucun des trois, seul ou combiné, n'égale la fiabilité/fraîcheur/couverture qu'offrirait ACLED avec un vrai accès — **ACLED est structurellement hors de portée gratuite pour ce projet**, pas juste "à négocier".
4. **Ne pas faire :** ne pas utiliser l'API GEO 2.0 de GDELT (mort, malgré la doc officielle) ; ne pas espérer d'accès ACLED gratuit sans affiliation institutionnelle ; ne pas présenter straits.live ou ISW comme des dépendances dures (side-projects/reverse-engineering sans SLA) ; ne pas vendre PortWatch/Kiel comme "live seconde par seconde" — ce sont des indices à J-2/J-5, très bien pour ce qu'ils sont, mal étiquetés ils deviennent un mensonge à l'utilisateur.

## Limites de cette recherche

- Le schéma exact des 61 colonnes de la GDELT Event Database 2.0 (noms de champs par position) n'a pas été retranscrit ici en intégralité — la doc officielle du format existe (`gdeltproject.org/data/lookups`) et devra être consultée précisément à l'implémentation, seule la présence/fraîcheur/taux de géolocalisation a été vérifiée empiriquement.
- Le comportement exact de `DecompressionStream('deflate-raw')` sur les fichiers ZIP GDELT n'a pas été testé bout-en-bout dans le navigateur (seule l'existence du fichier ZIP réel, son ratio de compression et l'API navigateur native ont été vérifiés séparément) — un spike dédié serait prudent avant de committer sur cette approche.
- Les tarifs des tiers ACLED "Research/Partner/Enterprise" (au-delà d'Open) n'ont pas été chiffrés (pages de vente non publiques/sales-gated) — impossible de dire si un palier payant existerait dans le budget 0-30 $/mois, l'hypothèse par défaut retenue est que non (produit orienté institutions).
- La pérennité de la couche ISW (endpoint ArcGIS non documenté officiellement comme API publique) et de straits.live (side-project mono-mainteneur) n'est garantie par aucun des deux éditeurs — traiter comme dégradable, jamais comme socle.
- Pas de test de charge/volume sur un polling GDELT 15 min prolongé (bande passante réelle cumulée sur 24h non mesurée en continu, seule une tranche a été téléchargée).
